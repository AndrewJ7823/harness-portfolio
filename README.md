# AI 코딩 에이전트 하네스 — 이렇게 쓰고 있습니다

> Claude Code(와 Codex)에게 신규 기능 개발을 맡길 때, **에이전트가 정해진 절차대로만 움직이도록 감싸는 작업 환경(하네스)** 을 직접 만들어 쓰고 있습니다.
> 이 문서는 그 하네스를 **어떤 생각으로, 어떻게 쓰고 있는지**를 정리한 것입니다. 내부 구현(가드·판정 도구·설정 구조 등)은 다루지 않습니다.

---

## 한눈에 보기

| | |
|---|---|
| **무엇** | 기능 1건을 `티켓 → 스펙 → 사람 승인 → TDD 구현 → 검증 → 기록 → PR`까지 끌고 가는 에이전트 작업 환경 |
| **왜** | 에이전트는 빠르지만, "다 했습니다"를 그대로 믿을 수 없고, 한 번 실수하면 외부 시스템에 실제로 영향이 간다 |
| **내 역할** | 판단이 필요한 세 지점(스펙 승인 · diff 검토 · 머지)에만 들어간다. 나머지는 에이전트가 진행한다 |
| **운영 방식** | 사고나 마찰이 실제로 생겼을 때만 규칙을 추가한다. 하네스도 하나의 제품처럼 개선한다 |

---

## 1. 왜 만들었나

에이전트에게 기능 개발을 그냥 맡겼을 때 반복해서 부딪힌 문제는 이런 것들이었습니다.

- **"대표 케이스 몇 개"만 테스트하고 끝낸다.** 테스트는 다 통과했는데 경계값 하나 때문에 배포 후 회귀가 났다.
- **계획 없이 바로 코드부터 쓴다.** 리뷰 단계에서 방향이 틀린 걸 알면 되돌리는 비용이 크다.
- **"완료했습니다"를 확인할 방법이 없다.** 결국 내가 "정말 다 봤어?"를 매번 직접 따져 묻게 된다.
- **안전 사고 가능성.** 개발 환경도 실제로 메시지가 발송되는 구조라서, 테스트 한 번 잘못 돌리면 외부로 나간다.
- **똑같은 지시를 반복한다.** "PR 상태 확인해줘", "리뷰 코멘트 처리해줘"를 PR마다 다시 말해야 했다.

그래서 **절차와 판정을 에이전트의 선의에 맡기지 않고, 환경 자체에 넣기로** 했습니다.

## 2. 어떻게 쓰고 있나 — 기능 1건의 흐름

### 시작은 명령 하나

```
/develop-feature PROJ-1234
```

손에 무엇이 있느냐에 따라 시작점이 세 가지입니다.

| 손에 든 것 | 에이전트가 하는 일 |
|---|---|
| 티켓 번호·링크 | 티켓과 기존 작업 상태를 조사해 바로 스펙 작성으로 |
| 기능 설명 한 줄 | 비슷한 티켓이 있는지 먼저 찾고, 없으면 만들지 물어봄 |
| 에러 트래킹 링크 | 먼저 원인 조사 → "이 내용으로 티켓 만들까요?" → 승인 시 생성 후 스펙으로 |

### 내가 개입하는 곳은 세 군데뿐

```
/develop-feature PROJ-1234
  ├─ 조사 · 스펙 작성              (에이전트)
  ├─ 독립 검토자의 반박 검토        (에이전트)
  ├─ ▶ "스펙 승인"                 (나)
  ├─ 테스트 먼저 → 구현            (에이전트)
  ├─ 기계 검증 · 작업 기록          (에이전트)
  ├─ ▶ diff 보고 "커밋해줘"        (나)
  │     └─ 커밋 · 푸시 · PR · CI · 자동 리뷰 대응까지 에이전트가 처리
  └─ ▶ 머지 · 배포                 (나)
```

실제로 제가 하는 말은 거의 이 두 마디입니다.

| 내가 하는 말 | 의미 |
|---|---|
| **"스펙 승인"** | 이 말이 나오기 전에는 제품 코드를 한 줄도 쓰지 않는다 |
| **"커밋해줘"** | 커밋부터 PR 생성, 상태·CI·리뷰 확인까지 한 번에 끝낸다 |

스펙에서 결정하기 어려운 부분(스키마 변경, 공용 계약 변경 등)이 나오면 에이전트가 멈추고 저에게 물어봅니다.

### 대화는 대략 이렇습니다

```
나   : /develop-feature PROJ-1234
에이전트: 스펙 작성 완료 — specs/PROJ-1234-….md
          케이스 18건 · 데이터 변경 없음 · 외부 의존 1건(mock 처리)
          독립 검토 지적 4건 / 반영 3건 (1건은 판단이 필요해 질문으로 올림)
나   : (요약과 케이스 목록을 보고) 질문 1은 A로. 스펙 승인
에이전트: … 구현 · 검증 완료. 케이스 18/18 커버, 전체 테스트 통과, 로컬 스모크 일치
나   : (diff 검토) 커밋해줘
에이전트: PR: https://github.com/…/pull/…
          머지 가능 상태 · CI 통과 · 자동 리뷰 코멘트 2건 처리 완료
```

## 3. 지키고 있는 원칙

**① 스펙이 먼저다 (spec-first)**
기능 1건에 스펙 1건. 스펙에서 가장 중요한 건 **케이스를 빠짐없이 나열하는 것**입니다. 정상 흐름뿐 아니라 분기, 경계값, 에러·권한, 동시성까지 축별로 전부 적고, 이 목록이 그대로 테스트 목록이 됩니다. BDD(티켓) → SDD(스펙) → TDD(구현) 순서를 따릅니다.

**② 에이전트의 "다 했습니다"를 믿지 않는다**
"테스트가 통과했다"가 아니라 **"스펙의 케이스가 전부 테스트로 증명됐다"** 를 완료 조건으로 둡니다. 판정은 에이전트의 자기 보고가 아니라 도구가 합니다.

**③ 쓴 사람과 검토하는 사람을 분리한다**
승인 요청 전에, 스펙 작성 맥락을 전혀 모르는 별도 검토 에이전트가 빠진 케이스와 계약 모순만 찾아냅니다. 사람이 거치는 단계는 늘리지 않으면서 검토 품질을 높일 수 있었습니다.

**④ 안전은 여러 겹으로**
외부 실발송 0건, 운영 환경 접속 금지, 자격증명·개인정보 출력 금지. 이 규칙은 문서에만 적어 두지 않고 **도구 차원에서도 막습니다.** 에이전트가 우회하려 하면 그 자체를 설계 오류 신호로 봅니다.

**⑤ 판단은 강한 모델, 반복 작업은 가벼운 모델**
케이스 나열·계약 설계·안전 판단처럼 완결성이 중요한 단계는 추론 성능이 높은 모델이 직접 맡고, 보일러플레이트 같은 기계적인 작업만 하위 에이전트에 맡깁니다.

## 4. 하네스를 키우는 방식

하네스는 한 번 만들고 끝나는 게 아니라 **계속 손보는 제품**입니다. 다만 규칙이 무작정 늘어나면 에이전트도 사람도 느려지기 때문에, 몇 가지 원칙을 정해 두었습니다.

- **실제로 사고나 마찰이 있었을 때만 규칙을 추가합니다.** "있으면 좋을 것 같다"는 근거로 보지 않습니다.
- 반복 단계가 늘어나는 규칙을 하나 넣으면 **기존 규칙 하나를 뺍니다** (one-in one-out).
- 규칙마다 **왜 생겼는지 근거를 기록해 둡니다.** 나중에 맞지 않는 규칙을 지울 때 근거를 보고 판단할 수 있습니다.
- 작업 기록에는 지표 한 줄을 남겨, 규칙을 바꾼 뒤 실제로 효과가 있었는지 확인합니다.

### 실제로 이렇게 바뀌어 왔습니다

| 겪은 문제 | 바꾼 것 |
|---|---|
| 경계값 케이스가 빠져 배포 후 회귀 | 승인 전 독립 반박 검토 단계 추가 |
| PR이 뒤처질 때마다 내가 직접 알려줘야 함 | 에이전트가 스스로 감지해서 보정하고 결과만 알려줌 |
| PR마다 자동 리뷰 코멘트 처리를 다시 지시 | 리뷰가 끝날 때까지 기다렸다가 코멘트를 모두 처리 |
| 이미 머지된 브랜치에 후속 커밋을 푸시하는 경합 | 확인과 푸시를 분리하고, 도구 차원에서도 차단 |
| 테스트를 폴더째 돌렸다가 외부 시스템이 실제로 호출됨 | 해당 레포는 테스트 파일을 하나씩 지정해서만 실행 |
| 화면 변경을 승인한 뒤 미리보기에서 수정이 반복됨 | UI 명세와 텍스트 와이어프레임을 승인 전에 확정 |
| 에이전트별 메모리에 흩어진 지침이 팀과 공유되지 않음 | 지침은 모두 저장소 문서에 기록 |

## 5. 쓰면서 달라진 점

- **리뷰 포인트가 코드에서 스펙으로 옮겨갔습니다.** 케이스 목록이 맞는지만 보면 되니 diff 검토가 가벼워졌습니다.
- **"다 봤어?"를 묻지 않게 됐습니다.** 커버리지가 숫자로 나오기 때문입니다.
- **반복 지시가 사라졌습니다.** PR 상태 확인, 리뷰 대응, 브랜치 보정은 에이전트가 알아서 처리합니다.
- **새 프로젝트에도 금방 옮길 수 있습니다.** 절차와 판정은 그대로 두고 프로젝트별 값만 채우면 되는 템플릿 형태로 정리했습니다. 도입도 에이전트가 대상 레포를 읽기 전용으로 살펴보고 초안을 채워 줍니다.
- **Claude Code와 Codex가 같은 규칙으로 움직입니다.** 실행 규칙을 에이전트 종류와 상관없는 문서 하나로 관리합니다.
